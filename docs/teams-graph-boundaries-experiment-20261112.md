# Teams Graph 读取能力：真实租户实验

实验时间：2026-11-12 03:14–03:21 UTC（北京时间 11:14–11:21）。
代码基线：origin/main `68dba0d7`，隔离分支 `investigate/teams-links-20261112`。

## 结论

Graph 足以支持通用的消息定位、聊天历史、频道线程、搜索定位后精读。
它不是任意查询数据库：聊天与频道支持的查询不同，部分无效组合会返回 200 并忽略条件。
接口必须根据资源类型规划请求、报告真实覆盖范围，不能把 HTTP 成功等同于查询语义成功。

## 方法与范围

- 使用当前登录账户的 delegated auth，Graph `v1.0`。从在线 SQLite 用只读连接备份认证库，
  token 刷新只写私有实验副本；没有修改在线认证配置或扩大授权。
- 三轮共 93 次 Graph HTTP 请求：82 次 GET，5 次只包含 GET 子请求的 `POST /$batch`，
  6 次只读 `POST /search/query`。不含 OAuth token 刷新。
- 抽样两个聊天、一个已加入 team 的一个频道、一个有 7 条回复的线程，及三个搜索命中。
  发现聊天时读取最近聊天的一页；发现频道时只取一个已加入 team，不扫描全租户消息。
- 每轮总超时 8 分钟、HTTP 超时 20 秒、单响应读取上限 4 MiB；最大并发为 2。
  没有做限流压力测试，没有发送、修改或删除消息，也没有调用 helper 生命周期入口。
- 证据只保留状态、耗时、字节数、字段名、时间边界、计数和散列标识。
  不输出 token、消息正文、摘要、参与人姓名或原始资源 ID。

当前 read token 实际含 `Chat.Read`、`ChannelMessage.Read.All`、`Team.ReadBasic.All`、
`Channel.ReadBasic.All` 等较多权限；full token 对同一聊天和频道也均返回 200。
这只证明当前身份可读这些样本，不证明默认配置具备同样权限，也没有证明最小授权组合。
read/full 是 CXP 认证 profile 名称，不能据此断言 token 的每项权限都只读。

## 聊天消息

| 实验 | 观察 | 对接口的约束 |
| --- | --- | --- |
| 聊天信息、按 ID GET 消息、`/me/chats/{id}/messages` 别名 | 200 | 链接应直接定位，不从最新消息扫描 |
| `$top=1/20/50` | 200；`0/51/100` 为 400 | 每页上限 50，不能把请求条数当实际返回条数 |
| 创建时间、修改时间降序 | 200 | 显式选择排序字段 |
| 两个时间字段升序、ID 降序 | 400 | 不提供虚构的服务器升序能力 |
| 创建时间 `lt`，搭配创建时间降序 | 200，结果满足条件 | 高效读取旧锚点之前的消息 |
| 创建时间 `gt/le/ge/eq`，搭配相同字段排序 | 400 | “锚点之后最近 N 条”没有已验证的直接查询路径 |
| 修改时间 `lt/gt`，搭配修改时间降序 | 200，结果满足条件 | 可查修改窗口，但不等同于创建窗口 |
| 创建时间过滤＋修改时间排序 | 200，但首轮 50 条中 24 条、次轮 50 条中 26 条违反过滤 | 必须内部校验组合，不能透传任意 OData |
| 创建时间 `<2000-01-01`，不指定排序 | 200，50 条全部违反过滤 | 缺少排序也会静默忽略过滤 |
| 同一空窗口过滤＋匹配的排序 | 200，0 条且无 nextLink | 对照实验确认过滤是否生效 |
| 集合 `$search/$count/$skip`、`contains(body/content,...)` | 400 | 搜索应使用独立 Search API |
| 聊天消息下 `/replies` | 404 | 聊天不能套用频道回复路由 |

首轮 `$top=50` 只返回 46 条，仍有 `@odata.nextLink`；过滤页返回 22 条也仍有下一页。
因此只有 nextLink 的有无能说明服务器是否提供续页，不能用 `len(items)<top` 判结束。
按原始 nextLink 翻两页各 5 条没有重复；另一聊天连续四页共 200 条没有重复，仍有后续。
这是有界观察，不证明并发编辑、删除期间分页没有重复或遗漏。

首轮检查器按时间字符串比较，`modified_lt` 的降序检查出现 false；这种比较不能可靠判断
精度不同的 ISO 时间顺序。次轮改用 RFC3339Nano 解析后的时间比较，修改时间查询
降序逆序数、非法时间数、过滤违例数均为 0；不把首轮 false 作为服务器乱序证据。

## 频道与回复

| 实验 | 观察 | 对接口的约束 |
| --- | --- | --- |
| joinedTeams → channels → 主帖列表/单条 → replies | 均 200 | 当前账户可读样本频道，无需 helper 创建该对话 |
| 回复列表 `$top=5`，沿 nextLink | 第一页 5 条，第二页 2 条且结束 | 完整线程需要处理回复分页 |
| 回复 `$top=51`、创建时间升序或过滤 | 400 | 不复用聊天的时间查询参数 |
| 频道主帖列表创建时间降序 | 400 | 不把频道列表解释为聊天时间线 |
| 频道列表 `$top=1&$expand=replies` | 200，一个主帖带 7 条回复 | 扫描主帖时可减少逐帖请求 |
| 单条主帖 GET 加 `$expand=replies` | 400 | 已知主帖仍应使用其 `/replies` 路由 |
| `/messages/{root}/replies/{reply}` | 200 | 回复 ID 与根消息 ID 必须分别保留 |
| 同一回复 ID 放在 `/messages/{reply}` | 404 | 回复链接不能按根消息路由读取 |

官方说明频道列表按**整条回复链的最近修改时间**排序，不能用主帖创建时间推断列表覆盖。
列表 expand 官方最多内嵌 200 条回复，其后还有独立的 `replies@odata.nextLink`。
本次只验证 7 条回复的 expand，没有验证超过 200 条时的行为。
依据：[频道消息列表](https://learn.microsoft.com/en-us/graph/api/channel-list-messages?view=graph-rest-1.0)。

## 字段投影：实测可用，未获文档契约保证

聊天集合、单条聊天消息、频道集合、回复集合的 `$select` 均返回 200，并实际只给指定字段。
例如单条消息从 1729 B 降到 249 B；一页 50 条消息完整响应约 78 KB，
仅 ID 与两个时间字段约 6.5 KB。后者不是严格冻结数据的配对基准。

但相关 endpoint 文档明确说其他 OData 参数不支持，不能把本次 `$select` 成功当作长期契约。
可用于可退化的内部优化，需检查返回字段；遇不支持应回退完整 GET，再本地投影。
不能依赖它保障读取正确性或稳定的网络字节上界。

证据中投影测试的 `invalid_dates` 表示响应未请求时间字段，**不是 Graph 返回非法时间**。
次轮频道测试统一附带的 `predicate_violations` 只对真正携带 filter 的测试有意义；
例如 expand 测试里的该计数不表示 expand 失败。

## 搜索与精读

`POST /v1.0/search/query`，`entityTypes=["chatMessage"]`：

- 不存在的标记词：200、0 个命中；`graph`：200、返回请求的 3 个命中。
- 三个命中都有非空 summary，resource 均无 body；按命中的 chatId/message ID GET，
  三条都返回 200、有正文且 ID 匹配，验证了“搜索定位 → 精读原文”的完整路径。
- 显式 `fields=[id,chatId,body]` 仍返回 200，但 resource 仅有 id/chatId，没有 body。
  搜索投影不能替代读取原消息。
- 自定义创建时间排序：400；KQL `graph sent<2000-01-01`：200、0 个命中。
  时间条件仅做了空窗口对照，未验证复杂 KQL 或特定聊天范围约束。
- 一次返回 3 条的响应中，`total=6047`、`moreResultsAvailable=true`。
  官方页面却说 Teams 的 total 是本页条数；这是**实测与文档不一致**，不是已验证有 6047 个结果。
  接口应返回该值的来源与含义不确定性，不能用它证明读完或内容不存在。

搜索范围不是给定链接天然限定的聊天。当前只验证当前用户范围搜索；
不能通过先全局搜索再过滤少量命中，就声称完整搜索过某个聊天。
索引延迟、删除消息、频道回复命中到 parent 的定位、搜索深分页均未验证。

官方文档说明搜索只覆盖当前用户有访问关系的消息、返回字段不完整、不能自定义排序。
这些是文档边界，不是本次通过未授权资源做出的实验结论。
依据：[Teams 搜索](https://learn.microsoft.com/en-us/graph/search-concept-chat-messages)、
[v1.0 Search Query](https://learn.microsoft.com/en-us/graph/api/search-query?view=graph-rest-1.0)。

## 请求合并与延迟

相同两条消息的 ID 投影读取，共用 token 和 HTTP client，每种方式做三次。
耗时记录到收到响应头；同一小响应读取开销未单独计入各 GET 的 `ms`。
组合耗时覆盖两条读取完成；batch 的 `ms` 也到响应头，不是完整 CLI 启动耗时。

| 方式 | 三次耗时（ms） | 中位数（ms） |
| --- | --- | --- |
| 串行 GET 两条 | 1405、1039、1292 | 1292 |
| 并发 2 个 GET | 789、716、517 | 716 |
| 一个 batch，2 个 GET 子请求 | 541、463、402 | 463 |

本地样本支持合并独立读取，但样本量很小、顺序固定、没有随机化或网络控制，
不能承诺 batch 在所有环境下更快；依赖锚点返回的查询也不能省掉依赖轮次。

20 个 GET 子请求的 batch：外层 200、20 个子响应都是 200；21 个：外层 400。
外层 200 不保证每个子请求成功，接口须按子请求 ID 匹配和处理状态。
本次没有混合失败子请求，也没有测试 429；20 的边界也见
[Graph JSON batching](https://learn.microsoft.com/en-us/graph/json-batching)。

## 对通用接口的具体影响

1. 裸 read 直接读取链接目标；前文、近期、回复和搜索是显式选择，不推断接手任务。
2. 已知旧消息先按 ID GET，再用真实创建时间＋匹配降序读取前文。
   修改时间 `gt` 不能冒充“此后创建的消息”。
3. 聊天和频道使用不同 planner。频道回复保留 parent，已知主帖用 replies；
   枚举多个线程时才考虑列表 expand，且同时处理主帖与回复两种续页。
4. 只允许已验证的查询组合。跟随受限同源 nextLink，按预算停止并显式返回未覆盖范围。
5. 搜索作为独立能力返回候选与来源；按需批量精读，不拿 summary 代替原文或把未命中当无记录。
6. 合并请求、连接复用、适度并发和可退化的字段投影属于执行优化，均不替 agent 决定读取范围。

## 尚未证明的边界

未测试未加入/未授权频道、最小 scopes、跨租户/共享频道/来宾、会议聊天的全部变体、
历史保留策略、删除或编辑竞态、同毫秒锚点、附件文件下载、托管图片内容、
429 与 Retry-After、超长消息/超大线程、索引一致性和深分页上限。
404 也不能仅凭状态区分不存在与不可见；当前没有为这些分支扩大授权或人为制造数据。
本实验只描述一个租户、当前登录身份与有限样本的能力，不推广到所有 Graph 身份或云环境。

后续另做了附件内容实验，成功读取图片及文件内容样本，详见
[附件访问补充实验](teams-graph-attachments-experiment-20261112.md)。
上述 93 次请求与未验证范围描述的是原三轮实验，不包含该补充实验。

## 复现与证据

附件包内 `graph-evidence.jsonl` 合并三轮记录，并加 `round` 字段；保留原检查器的限制，解释见上文。
证据的 count 是集合 value 的长度，单资源 GET 的 count=0 不表示资源不存在。
附件 `graph-probe-source.zip` 含证据、独立 Go 探针、认证库只读备份脚本和设计文档，不含任何认证库。
Go 探针须放到同一仓库模块下才能引用 internal 包；不要以 source-built cxp 启动在线服务。
认证路径、输出路径由显式环境变量指定；输出目录须事先验证可写。
实验只改变研究文件与本文档，没有为 Graph read 实现产品命令。
