## Why this prerelease exists

`v0.1.14-rc.13` fixes a runtime-identity split in the Teams model surfaces. The Teams agent executor already selected CXP's managed Codex installation for the target account, but `model list`, official-model resolution, login probing, the unified model gateway, and Beacon diagnostics could still resolve a bare `codex` from the helper service's inherited `PATH`.

That assumption is false for a correctly isolated service. CXP deliberately keeps its private managed npm prefix out of the service `PATH`, and the service may execute for a different target account with a different `CODEX_HOME`. The result was especially confusing: normal agent turns could work while `model list` omitted every official GPT model or reported the account as logged out. The previous integration tests injected a Codex path directly, so they proved catalog parsing but did not prove the production runtime-discovery path.

This candidate makes the executable, environment, target identity, and cache identity one explicit contract shared by every Teams Codex consumer.

## Runtime-contract corrections

- Resolve the CXP-managed Codex launcher independently of the helper service `PATH`, using the same effective Teams target account, working directory, user PATH policy, managed npm prefix, and `CODEX_HOME` as real agent execution.
- Silently install the managed Codex runtime on first use when it is not present yet. The install remains constrained to the managed prefix, runs as the configured target identity, and preserves the configured proxy/profile environment.
- Pass the complete runtime contract to login probes, bundled-catalog reads, app-server `model/list`, official model switching and forking, and unified official/third-party gateway preparation.
- Keep explicit `--codex-path` behavior explicit: named commands are resolved inside the target environment, absolute paths must exist, and no unrelated service-account executable is substituted.
- Report a real runtime or login failure in `model list` instead of silently presenting it as an unauthenticated account. Verified third-party profiles remain visible with the diagnostic.
- Cache official catalogs by a fingerprint containing the canonical executable, binary revision, target `CODEX_HOME`, target PATH, platform, and execution identity. A Codex upgrade explicitly invalidates the cache.
- Use managed-runtime discovery in Beacon bootstrap diagnostics. A worker configured for automatic managed installation is no longer rejected merely because a naked `codex` executable is absent from the scheduler or container PATH.

## Regression prevention

- Add a first-use test proving a missing managed runtime is installed without requiring an earlier agent turn.
- Add service-PATH isolation coverage proving the private managed launcher is found even when no `codex` command is visible to the service.
- Add shared-contract tests proving Teams model listing, login probing, official resolution, and unified profile preparation observe the same executable, `CODEX_HOME`, environment, and runtime fingerprint.
- Add cache tests proving account homes and binary revisions cannot share an official-model catalog, and upgrades clear stale entries.
- Add a source audit that fails when new Teams or Beacon consumers introduce an unreviewed bare-`codex` lookup, plus a wiring guard for the production Teams constructors. These development-only audits skip only in packaged static-binary smoke containers where the source tree is intentionally absent; present-but-unreadable or changed source still fails closed.
- Strengthen the gated live routing workflow so Codex is installed only in a private CXP-managed prefix that is deliberately absent from the service PATH. The workflow now verifies both the real Teams official catalog/resolver and the existing GPT-to-NVIDIA-to-GPT route.
- Bind the live test to the supplied managed prefix so package-test HOME isolation cannot accidentally install or select a second Codex runtime.

## Compatibility and user experience

- Users with no third-party profiles retain the native official Codex path and existing model behavior.
- Users with verified third-party profiles continue to see official models first when the target account is signed in, followed by verified external models.
- Users who intentionally use only third-party models are not required to expose Codex in the service PATH; CXP still supplies the managed app-server runtime required to host those models.
- Existing profile verification, backup-JSON warnings, model switching generations, queued-turn pinning, reasoning-effort correction, and thread recovery semantics are unchanged.
- Runtime discovery and installation are automatic during normal `model list`, switch, fork, and turn preparation. Action is requested only when authentication, installation, or configuration genuinely cannot be completed.

## Qualification plan

- Focused runtime-contract, catalog, resolver, login, unified-gateway, Beacon, cache, wiring, and bare-command audit tests, including race detection.
- Full uncached Go suite with the main-CI timeout and parallelism, `go vet`, actionlint, `git diff --check`, and Windows amd64 cross-compilation.
- Managed-Codex installation integration coverage.
- A real regulated-account test using the current CXP-managed Codex launcher and actual official catalog, verifying `gpt-5.6-luna` is visible and resolvable through the production runtime resolver.
- Main-branch GitHub Actions across supported platforms and release packaging, followed by the gated real model-routing workflow when repository opt-in credentials are available.
