# v0.1.22-rc.79

## Why

Teams progress could disappear after 20 messages, in group chats, during
queue or send pressure, or while catching up on history. Callback publication
also could not recover progress written while the helper was stopped. Retrying
a POST only because it was absent from a listing could duplicate an accepted
message whose response or visibility was delayed.

## What changed

- Remove the progress count limit, group suppression, pressure-based content
  replacement, and the catch-up filter for commentary and compaction records.
- Publish progress for new native work-chat executions from the incremental
  rollout reader. Callbacks wake that reader; the runner still owns prompts,
  final answers, statistics, and files. Persist ownership before native work
  starts and retain the stable client key across capacity retries and restart.
- Combine up to 16 adjacent complete progress messages of one execution within
  the existing Teams size limit. Freeze the payload and batch membership before
  sending. Preserve the original records, immutable retries, and source order.
- Persist a final in the existing outbox until preceding source records commit.
  Release the execution slot immediately, then release final parts at the source
  terminal position and wake delivery without waiting for maintenance.
- Keep substantive messages with unknown send results, issue one control warning,
  and check again at the normal backoff cadence. Do not blindly resend or discard
  them. Other chats can proceed. Retain permanently rejected content with an
  explicit warning, and preserve a definite rejection received during shutdown.
  This also retains legacy progress rows that have no new batch-group marker.
- Restore visible still-working notices: first after two minutes, then at
  five-minute intervals. Keep tool activity separate from visible output and
  avoid building a queue of periodic notices behind pending content or questions.
- Bound reader work and pending publication, leave unread content in the source,
  preserve partial-record repair, and give aged catch-up content paced send slots.
  This uses the existing reader, outbox, sender, and account send budget.

## Validation

- The complete ordinary Go suite and all 15 process E2E scenario packages pass
  through the development skill's isolated Docker harness. The final source is
  integrated with the latest main, including startup recovery and native input
  routing fixes. Core/channel race checks and focused repeated recovery checks
  cover the changed paths; main CI and the release workflow verify this commit.
- Regression coverage includes 120 ordered group-chat progress records through
  429 and restart, 1,000-record backpressure with one execution slot, accepted
  batch POST followed by a crash, ambiguous delivery with late read-back,
  terminal/outcome commit races, previous capacity attempts after restart,
  consecutive final-answer wakeups, partial records, and historical compaction.
- Vet, CGO-disabled Windows amd64, macOS amd64/arm64, and Linux arm64 builds,
  and three rounds of actual Codex 0.166.0 offline protocol checks pass.
- The resource audit covers an 814 MB store with 1.18 million inbound and
  450,000 outbox rows. Hot paths use indexes. Migrating a 28.4 MB old outbox
  took about 107 ms and added one 4 KiB page. Unchanged/read-only paths do not
  rewrite message bodies. A 100,000-request ownership index retained about
  14.2 MB and loaded in about 100 ms on the development machine.
- Stable fallback identities for 1,000 ID-less records add about 5.6% parse
  time and 7.8% allocation bytes against the base revision. Large tool-output
  head classification remains about 0.5 microseconds. These measurements do
  not predict network throughput or every platform's performance.

## Compatibility

- The CLI base version remains v0.1.22. Store schema v4 adds publication ownership,
  final holds, and frozen-batch metadata without rewriting historical bodies.
  Older binaries that understand only schema v3 cannot open the upgraded store.
- Old helper executions do not become eligible for automatic historical replay.
  Previously discarded content behind an advanced cursor is not backfilled.
  Catch-up preserves the content that remains unread, without old completion
  notifications. No running helper is updated or restarted by this source release.
- An unknown external POST result is not proof of delivery or rejection. Without
  external idempotency, automatic eventual delivery and zero duplicates cannot
  both be guaranteed for every ambiguous network failure. The helper retains
  the content and reports the uncertainty instead of hiding that distinction.
- Local process E2E tests use private state and fake Graph/Codex services.
  Actual Codex checks are offline; live Teams delivery was not reproduced.
