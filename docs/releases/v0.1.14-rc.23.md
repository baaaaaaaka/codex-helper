# v0.1.14-rc.23

## Why this prerelease exists

Teams work chats can carry files between two signed-in `cxp` machines, but the
old path treated the Teams message as the transfer itself. That created three
failure modes:

- a large upload could be mistaken for a stuck request because the default
  30-second HTTP timeout covered the whole body transfer;
- a process restart or a transient network failure could lose the upload
  position and repeat the entire transfer;
- a file sent by the helper could later be observed by the receiving helper as
  an ordinary user attachment when the message history was replayed.

This candidate makes file transfer durable and makes helper-message detection
fail closed, while keeping ordinary Teams control requests responsive.

## What changed

- Files at or below 10 MiB continue to use a single Graph upload request.
  Larger files use a resumable Graph upload session with sequential 10 MiB
  chunks. The chunk size is a multiple of Graph's 320 KiB fragment unit and is
  independent from the application's separate 250 GB single-file ceiling.
- File-transfer requests no longer inherit the 30-second whole-request
  control timeout. They use bounded connection and response-header timeouts,
  an idle-body watchdog that resets on progress, bounded retries, and a small
  per-host transport pool. Uploads remain sequential so one transfer cannot
  create a connection or port storm.
- Outbound attachments are staged privately, hashed with SHA-256, and tracked
  in the durable outbox. Upload-session URL, expiry, and acknowledged offset
  are checkpointed with attempt fencing and throttled persistence. A restart
  can resume a valid session, while malformed or regressed server offsets fail
  closed and expired sessions are recreated in a bounded way. DriveItem
  publication is fenced by the same send-attempt lease, so a stale worker
  cannot attach its result to a newer retry. While a chunk is in flight, a
  local lease heartbeat renews the outbox without opening another Graph
  request or parallelizing the upload.
- Downloads stream into a private `.part` file with metadata and a lock,
  resume only after validating `206` and `Content-Range`, refresh expired
  preauthenticated URLs, call `fsync` before preserving partial data, and
  publish only after the final size/range checks. Failed downloads retain
  bounded, recoverable partial state; successful publication removes the lock
  residue.
- Helper-generated messages carry an internal provenance marker, but the
  marker is accepted only when it matches a durable outbox record for the same
  chat, message ID, attachment, and live transfer state. A marker by itself is
  never enough to suppress a user message. Existing global direct-send
  provenance remains scoped and is still checked exactly.
- Startup reconciliation cleans abandoned staged files without following
  symlinks or deleting paths outside the configured outbox. Temporary files
  use private names and are published without replacing an existing staged
  artifact.

## Reliability and compatibility

The 30-second timeout remains for Graph metadata, upload-session creation, and
Teams message POST control operations. It is not a deadline for transferring a
file body. The transfer implementation uses no background worker or listener,
keeps its connection pool bounded, and does not create a new process or port
per chunk. Direct `send-file` remains compatible with the existing scoped
outbound provenance ledger; the durable outbox is authoritative for bridge and
automatic attachment delivery.

## Test and CI coverage

The candidate was validated with:

- `go test ./...`;
- `go vet ./...`;
- `go test -race ./...`;
- focused upload-session checkpoint, offset fencing, resumable download,
  preauthenticated URL refresh, slow-body timeout, transport-pool reuse,
  provenance, staging, and SQLite/JSON persistence tests;
- Windows cross-compilation of the affected CLI, Cloudgate, and proxy test
  packages;
- explicit CI execution in the core shard, Linux distro containers, the
  non-root container path, and the prerelease workflow.

This is a prerelease for validating the Teams file-transfer path. It does not
replace the existing stable `v0.1.14` release.
