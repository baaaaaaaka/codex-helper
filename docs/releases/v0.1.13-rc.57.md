# Teams managed-runtime update activation reliability

This prerelease fixes a Teams helper self-update failure in the immutable-runtime update path. The update could successfully publish and activate the requested runtime, yet the helper later reported an activation mismatch and continued running the previous version after its restart.

## Root cause

The immutable-runtime design intentionally keeps the current helper process on its existing version until a restart crosses the stable `cxp` entry and dispatches the active runtime. Two parts of the update flow treated that expected transition as if it were a legacy in-place replacement:

- Before applying an update, Teams compared the running executable path with the stable install path. A process running from `.cxp-runtime/versions/<old-version>/cxp` therefore looked physically different from the stable entry and was marked as requiring deferred activation.
- The installed-path restart inherited `CXP_RUNTIME`, `CXP_RUNTIME_ROOT`, `CXP_RUNTIME_VERSION`, `CXP_ENTRY_PATH`, `CXP_RUNTIME_DISABLE`, and `CXP_RUNTIME_FORCE`. Those variables identify an already-dispatched runtime process. Carrying them into the stable launcher made it skip active-runtime dispatch and could leave the restarted helper on the old version.

The active pointer and fresh stable-entry probe had already verified the new runtime, but the stale pre-update decision and inherited process identity overrode that successful state.

## What changed

- A successful `RuntimeActivated` result is now the authoritative postcondition for managed immutable-runtime updates. It clears only the pre-update physical-path mismatch so Teams uses its normal fresh-launch restart.
- Managed-runtime results that simultaneously claim a legacy pending replacement or `RestartRequired` state are rejected as contradictory instead of guessing which activation mechanism should win.
- Restarts through an explicit installed helper path now remove all six runtime-control variables while preserving unrelated environment values.
- Unix continues to replace the process with `exec` and the sanitized environment. Windows now passes the same explicit environment to the spawned replacement process before the old helper exits.
- Development reloads and generic non-runtime restart paths retain their existing environment behavior. Legacy direct-binary replacement, including Windows pending-replacement handling, is unchanged.

## Safety and platform behavior

- Linux foreground and systemd launches, macOS foreground and launchd launches, WSL task launches, and Windows foreground or scheduled-task launches all converge through the stable entry and its atomically selected active runtime.
- The fix does not mutate or replace the currently running immutable runtime. Activation remains an atomic pointer update followed by a fresh process boundary.
- A managed update is not reported as active merely from path inference: the downloaded runtime and the fresh stable entry must still pass the existing version probes before the update call succeeds.
- Unmanaged and older legacy installations continue to use the previous physical-path and pending-replacement decisions.

## Validation added

- A post-apply state matrix covers legacy immediate activation, legacy deferred activation, managed-runtime success, and contradictory result rejection.
- A managed-runtime updater fixture reproduces the old-runtime-path versus stable-entry mismatch and requires the normal restart path after activation.
- Cross-platform restart tests require the installed path and arguments to remain correct, all runtime-control variables to be absent, and unrelated environment values to survive.
- Native Linux, macOS, and Windows process smokes build `v0.1.13-rc.56` and `v0.1.13-rc.57` helpers. They prove that stale runtime markers pin the old version and that a fresh stable launch dispatches `v0.1.13-rc.57` through the active pointer.
- Main CI runs the focused activation suite and native process smoke in every platform-integration shard. Release preflight repeats the focused checks and process smoke on Linux, macOS, Windows Server 2022, and Windows Server 2025.
- The complete local Go suite, focused race tests, `go vet`, workflow lint, and Windows amd64 and macOS arm64 test-binary cross-compilation pass. The GitHub PR matrix completed successfully across all 32 latest jobs.
