# Teams agent CLI entry and runtime environment

## Why

A Teams agent could invoke an old CLI after a successful CXP update. The
app-server inherited launcher-only runtime markers, which made an old PATH
entry skip normal runtime selection. The advertised CLI path also pointed at
an immutable version binary; removing the markers alone could create a nested
runtime installation when that binary was invoked.

## What changed

- Supply the managed helper's owning stable installation entry and directory
  to Teams agents and login-shell PATH probes. Keep existing standalone path
  resolution and never choose another installation from PATH as a fallback.
- Remove the existing runtime and boot markers at the final app-server launch
  boundary, after environment and identity configuration, for both stdio and
  shared WebSocket processes. Preserve application environment and Teams
  self-management protection, including nil and explicitly empty environments.
- Update the bundled cxp skill with quoted POSIX and PowerShell examples,
  confirmed-runtime semantics and guidance for a missing or unusable entry.
- Add actual child-process regressions, a production-entry Teams scenario with
  an older dispatcher and newer active runtime, and explicit four-OS release
  preflight selection.

## Validation

Regression tests detect both original defects before the fix. Local validation
uses Go 1.25.11, isolated Docker for real helper processes and native Windows
for environment and entry-selection tests. The managed-entry scenario checks
version and Teams read help, login-PATH resolution, unchanged boot records,
no nested runtime installation and preserved helper self-management refusal.
Another turn checks that an existing agent follows an external confirmed
activation/rollback while its helper remains running.
The existing child-guard scenario checks stop, pause, restart and upgrade refusal
and a subsequent successful prompt.

The rc.3 Release run exposed an existing timing race in a model-switch test:
it killed the helper while a separate control notification was in flight. The
test now waits for that notification before testing model persistence across
a crash, retaining its behavior and transcript assertions.

The added environment pass takes about 2.25 microseconds for 64 application
entries and 14.6 microseconds for 512, with one allocation and no disk I/O. It
runs only at app-server startup. These are workload measurements, not latency
guarantees. See [the validation record](https://github.com/baaaaaaaka/codex-helper/blob/v0.1.23-rc.4/docs/teams-agent-runtime-validation-20261112.md)
for test entry points, environment restrictions and platform coverage.

Publication requires the main CI and complete Release workflow, including
native Linux/macOS/Windows preflights, the slow tier and packaged update tests.
Final GitHub run results are linked after validation completes.

## Compatibility

No runtime boot protocol, state schema, service registration or user PATH
change. The stable entry selects its current confirmed runtime, which can
differ from an already running helper's version. An unavailable owning entry
remains an explicit failure instead of silently selecting another install.

Existing app-servers keep their launch environment. Install the prerelease and
use the normal Teams control-chat update/restart lifecycle to obtain the new
behavior in future agent processes. This release does not repair unrelated
PATH entries or update/restart a running helper during development.
