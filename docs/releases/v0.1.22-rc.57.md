## Why

Make the Windows app-install CI exercise the same supported non-elevated path as users. GitHub-hosted Windows jobs run with an elevated token, so the new production safety guard correctly refused their installation smokes and exposed tests that depended on the runner's ambient token.

## What changed

- Make CLI test hooks report a deterministic non-elevated token by default; elevation-specific regressions continue to override the hook explicitly.
- Run Windows Store and CXP-managed app installation smokes with the existing runner user's linked limited token when available. If the hosted runner exposes no linked token, derive a restricted medium-integrity LUA token from that same user token; keep production elevation checks enabled in both cases.
- Verify the smoke token is not an effective Administrator and remove temporary smoke files afterward.
- Update the Go and Python CI contract tests to assert both limited-token app smokes remain selected.

## Validation

- Focused app-upgrade and elevation tests, Windows/amd64 test-binary cross-compilation, PowerShell parser checks for the Windows smoke scripts, and `git diff --check` passed locally.
- The root CI workflow contract test and 32-test shard-contract suite pass with the new selectors; the full `internal/cli` suite remains blocked locally by WSL-to-Windows PowerShell interop (`UtilBindVsockAnyPort`).
- The WSL-host token check derives the restricted token, but the caller lacks `SeImpersonatePrivilege` and cannot create its child (`ERROR_PRIVILEGE_NOT_HELD`, 1314); native Windows CI must verify the hosted runner can launch it and complete both app-install smokes.
- Require the new GitHub Windows jobs to pass before considering the limited-token install smoke validated.

## Compatibility

- No production elevation policy changes: native Windows install and upgrade still refuse elevated or unverifiable tokens; WSL and other platforms are unchanged.
- This CI correction does not resolve AppX package-identity startup failures or Windows Defender reputation reports. macOS same-bundle LaunchServices forwarding and OpenAI background-updater writes remain unverified; the accepted upgrade procedure still requires quitting all app instances and not reopening from Finder during the update.
