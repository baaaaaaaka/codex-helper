## Why

Stop extending a Windows CI token-emulation mechanism that has not passed native app installation tests. Restricting an elevated runner token did not reliably produce the normal user context required by the production installation policy.

## What changed

- For native Windows managed installation/update, use Microsoft's normal-parent process context mechanism only after verifying the desktop shell has exactly the invoking user's SID/session/profile/cache and is non-elevated. Keep the verified process handle open while creating the worker; do not adopt another desktop user's identity. The worker independently revalidates its actual token and target before writes, bypasses normal CLI/runtime dispatch, and returns verified installation state. No account switching, fabricated tokens, ACL changes, or elevated-write retry. Missing capability or process-creation failure requires a non-administrator rerun.
- Remove the linked/restricted-token native launcher and the source-string tests tied to its APIs and ACL workarounds.
- Use an isolated temporary account with its loaded native profile, and assert the actual production TokenElevation query before running the source-built helper.
- Separate policy tests, user-context probing, managed installation, and Store installation so one app backend does not hide coverage of the other.
- Keep deterministic policy-test hooks, prebuilt fixtures, and explicit process stream redirection; add native process-runner behavior tests.
- Preserve diagnostic logs and remove only processes belonging to the unique test account. Unsupported Store capability is a failure, not a silent skip.
- Prepare the Store account with Microsoft's documented App Installer registration command. Separately prepare the signed MSIX and its LocalSystem service with the elevated CI runner, then test registration and CXP launch in a verified standard account without winget; that result does not replace the Store installation gate.

## Validation

- Workflow/shard contracts (32 Python tests), focused CLI regressions, Windows/macOS test-binary cross-compiles, and diff checks passed. Native Windows PowerShell parsing, inert process-runner behavior tests, and the actual standard-token API assertion passed.
- Real UAC inert acceptance passed: an elevated parent delegated initial installation, unchanged refresh, and changed-package update to the same actual non-elevated identity; cancellation preserved the previous valid installation. Fake package/signature hooks were used, and no app was executed. Direct linked-token launch failed with an identification-level token; using an actual normal primary token still failed with privilege-not-held. Neither failed launch technique is retained as a fallback.
- The complete local Go run passed in the bundled ephemeral container (`go test ./... -count=1 -parallel=16 -timeout=20m`). Corrected test environment constraints rather than changing unrelated Teams/history production code or loosening filesystem permissions.
- UAC inert acceptance ran with Defender real-time protection enabled; this is not a guarantee against false positives for other unsigned release artifacts. Both read-only Store policy API controls pass on the native host; CI records each operation's outcome without masking a failed Store smoke.
- Native GitHub validation is pending. This note is not evidence that either installation smoke passed or that the original AppX startup report was fixed.
- Require the native standard-user probe, managed smoke, Store smoke, and all other required jobs before merging or publishing this candidate.
- Select the actual prerelease version from the latest published release at publication time; the filename is provisional.

## Compatibility

- No elevated managed-cache writes or new production app-registration mechanism. Only the managed installation worker can use a verified same-user normal token; the parent and app launch retain their intended privileges. Legacy Store installation still refuses elevated or unverifiable tokens. CI-only package preparation is not a production fallback; WSL and other platforms retain their existing behavior.
- Preserve the installer integrity fix, Windows managed image-path verification, and macOS stable-path upgrade implementation, subject to their outstanding native acceptance checks.
- This cleanup does not resolve unverified AppX identity or Defender reputation reports. The accepted macOS operational constraints and background-updater uncertainties remain unchanged.
