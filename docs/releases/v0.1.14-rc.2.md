## Why this prerelease exists

Teams previously chose reasoning effort only when the helper process launched. A Control or Work chat could not inspect the current model's supported effort values, could not change effort without rebuilding the executor, and could not safely capture a different value for later queued turns. This was especially limiting for long-lived chats where users want to trade latency for reasoning depth from one turn to the next.

This prerelease makes reasoning effort a durable per-chat setting while preserving the behavior of work that is already queued or running.

## What changed

### The same commands in Control and Work chats

Both chat types now support:

```text
effort status
effort list
effort set <value>
effort reset
```

`effort <value>`, `effort switch <value>`, `effort use <value>`, and `model effort ...` are accepted aliases. `effort reset` selects the current model's advertised default.

### Model-driven discovery instead of a hard-coded list

- `effort list` calls the active Codex app-server's paginated `model/list` method.
- The helper selects the exact model pinned to the chat, or the app-server default for an unpinned official chat.
- Supported effort values, descriptions, order, and future values are preserved exactly as advertised by Codex.
- A configured model missing from `model/list` fails closed instead of validating against an unrelated first model.
- Unsupported values and inconsistent model defaults are rejected before chat state changes.

### Durable per-chat state and exact queue snapshots

- Control and Work sessions persist both the selected effort and its source.
- JSON and SQLite stores capture effort on every queued turn alongside the model-profile snapshot.
- Changing a chat affects only turns queued after the command. Running and already queued turns keep their original effort.
- Retrying a new turn preserves its captured effort; legacy turns without a snapshot use the executor's effective default.
- Explicit launch configuration such as `model_reasoning_effort="medium"` remains authoritative until that chat is explicitly changed. The new feature does not silently replace an operator override with `xhigh`.
- Concurrent effort updates are serialized and keep the durable store and registry projection consistent.

### Local and Beacon execution use the same contract

- Local app-server turns send the captured value through `turn/start.params.effort`.
- Beacon jobs include the same effort in their fenced job payload.
- Remote Beacon workers pass that value to their own Codex app-server turn.
- The Responses adapter continues mapping provider-specific maximum effort correctly, including DeepSeek `xhigh` to `max` and MiMo `xhigh` to `high`.

### Third-party model catalog alignment

MiMo was already configured to enable provider thinking, but its generated Codex catalog did not advertise reasoning support. The catalog now reflects the existing adapter capability and exposes `low`, `medium`, `high`, and `xhigh` in deterministic order for reasoning-capable DeepSeek and MiMo models.

## Compatibility and defaults

- Existing Control chats keep the historical effective default of `low` until explicitly changed.
- Existing Work chats keep the historical effective default of `xhigh`, unless the helper was launched with an explicit `model_reasoning_effort` override.
- Old registry and store files remain backward compatible because the new JSON fields are optional.
- No SQL schema migration is required; SQLite row JSON carries the new fields.
- Chat model profiles, Codex thread bindings, approval behavior, and queue ordering are unchanged.

## Review fixes included before tagging

The prerelease review found and fixed issues that were not visible in the first implementation pass:

- preserved explicit operator effort overrides instead of overwriting them at queue time;
- rejected missing pinned models instead of falling back to an unrelated catalog entry;
- validated `effort reset` against the advertised supported list;
- serialized registry/store projection updates and added a race regression;
- aligned MiMo's generated catalog with its already-enabled thinking adapter;
- kept the Control fallback prompt within its bounded help budget after documenting the new commands.
