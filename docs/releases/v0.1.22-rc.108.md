# Restore automatic upgrades across the SQLite boundary

## Why

The SQLite-only release rejected the validation and updater protocol used by
supported older helpers. An rc.96 helper could download the new binary but
could not complete its automatic upgrade. The former artifact test accepted
that failure and then used the installer, so it did not enforce the user path.

## What changed

- Inert historical probes and a bounded migration adapter accept the original
  updater contract. The adapter verifies the candidate, source version and
  installation owner, then records the handoff in the existing native updater
  database. Normal runtime state remains SQLite-only.
- Old callers retain their read-back receipt and can finish their last state
  write before the first normal invocation publishes the native bootstrap.
  Old TUI trials transfer ownership before native writes. Incompatible old
  runtimes never become native rollback targets.
- On Windows, a single migration worker waits on mapped process handles before
  replacing the old launcher. A transient kernel token prevents duplicate
  workers. It handles a restarted service retaining the image without polling
  or repeatedly copying the executable. Native boot remains authoritative
  while that one-time forwarding receipt is needed.
- The TUI downloader shares the same verified bootstrap admission as manual
  updates while Windows retains an old image. An unverified forwarding receipt
  remains rejected. Migration tests wait for physical replacement without
  repeatedly launching the old image they need to release. They observe file
  size and modification time without opening executable read handles during
  replacement, then verify the complete replacement bytes and normal cleanup.
- The scan-throttle regression waits for two observed scans in each recovery
  round instead of assuming a fixed sleep covers runner scheduling delays.
  It keeps the original minimum scan-gap assertion and all three rounds.
- Failed or interrupted migration can retry without resetting a newer native
  selection or discarding its TUI trial. Lost published state fails closed.
  Completion removes the receipt and runs the deferred built-in skill refresh.

## Validation

The new regression runs the pinned rc.96 caller with its original downloader,
validator and updater; only the test download transport points to a local HTTP
fixture. It covers the old active-pointer and boot-protocol-one layouts, last
old-core writes, TUI handoff, native rc.104 upgrades, and Windows image locking.
The same test fails on the previous implementation at candidate validation and
passes with the fix. Four native OS jobs run it before publication.

The packaged-artifact gate now requires the original published updater to exit
successfully. It no longer copies the new binary or invokes an installer to
rescue a failed upgrade. The gate covers supported formal releases, rc.96 and
rc.104. Check the CI and release runs linked to this tag for native results.

Local validation uses focused Go tests, the full Go suite, related race tests,
Python script tests and isolated Docker lifecycle tests. A clean native startup
migration check performs no database open, executable hashing or writes; a warm
Linux benchmark measured about 1.7 microseconds at the physical entry and
3.7 microseconds in the runtime. These are workload observations, not latency
limits or measurements of the complete command.

## Compatibility

Supported older helpers can use their existing automatic upgrade command across
this boundary. Legacy decoding and receipts exist only for the one-time handoff;
there is no dual storage backend. Other old writers that share business state
must still be stopped or isolated before migration. Native boot protocol 2 and
the SQLite schemas remain unchanged. Downgrade after new state writes requires
restoring a consistent matching backup and executable together.

This release does not restart or modify an installed helper during development.
