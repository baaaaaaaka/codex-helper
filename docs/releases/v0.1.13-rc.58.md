# Cache v2: bounded SQLite writes without WAL or user configuration

This prerelease replaces the remaining codexhistory JSON caches and the
WAL-backed preview cache with one automatically managed cache generation. The
goal is to keep TUI preview and history discovery fast without turning a small
session append into a rewrite of tens of megabytes, while retaining safe
behavior on NFS and when multiple CXP TUI processes are open.

## Root cause

The previous cache stack had accumulated three different persistence models:

- session metadata and history indexes were serialized as whole JSON objects;
  changing one entry could rewrite the entire cache file;
- preview rows lived in SQLite WAL mode, which created persistent WAL/SHM
  activity and was not an appropriate default when the Codex data root is on a
  network filesystem;
- local and shared cache layers had separate versions, locations, ownership
  rules, and migration paths, leaving legacy files active or ambiguous after an
  upgrade.

This made write volume depend on total cache size rather than changed data and
made it difficult to state exactly which cache an installation was using.

## Unified cache generation and migration

- All codexhistory acceleration now uses cache version `2` under the selected
  Codex data root:
  `CODEX_DIR/.codex-proxy/codexhistory/v2/<effective-user-identity>/`.
- There is deliberately no separate cache-directory setting. Explicit
  `--codex-dir` selections and existing `CODEX_DIR` behavior automatically
  determine the cache location, including cluster deployments that place the
  Codex data root on larger shared storage.
- The single cache version applies to both `catalog.sqlite3` and
  `preview.sqlite3`. A future cache-version bump selects a new generation and
  rebuilds every cache from source JSONL; ordinary CXP upgrades keep the same
  generation and do not rebuild it.
- On first successful v2 use, CXP best-effort removes the current identity's
  known legacy metadata/history/preview JSON files, old preview SQLite
  database and sidecars, old shared JSON shards, and prior version directories.
  Other users' identity directories and legacy shards are never removed.
- Cache files are private to the effective Unix UID or Windows SID. Shared
  parent directories are sticky, so root and non-root runs do not overwrite one
  another's cache.

Session JSONL and `history.jsonl` remain authoritative. Cache open, permission,
lock, schema, or corruption failures fall back to source parsing. Corrupt or
incompatible databases are quarantined and rebuilt; a cache problem cannot hide
or delete conversation history.

## Minimal-write SQLite design

- Both databases use SQLite rollback journals with `journal_mode=DELETE`,
  `synchronous=NORMAL`, a short busy timeout, one connection per database, and
  no WAL or SHM files.
- Session metadata and history source cursors are stored as normalized rows.
  Exact hits perform no transaction; appends read only the complete JSONL tail
  and update only changed rows. A multi-session discovery batch commits once.
- Preview messages and dedupe identities are normalized by session and ordinal.
  Appends use compare-and-swap cursors and generations, so two TUI processes
  cannot commit the same tail twice. A losing process invalidates its stale
  in-memory baseline and reloads the winner instead of repeatedly conflicting.
- Small preview appends remain in a bounded in-process cache and are coalesced.
  Persistence occurs after the append reaches 64 KiB or a subsequent changed
  refresh observes a 30-second dirty age. An unchanged timer-driven refresh
  never writes merely because time passed.
- Append validation hashes a bounded 64 KiB split between the beginning and end
  of the previously parsed prefix. This catches an early in-place rewrite plus
  later append without rescanning an arbitrarily long conversation.
- In-memory preview state is bounded to 64 sessions and 16 MiB; dirty-path state
  is bounded to 1,024 entries.

The Linux syscall probe on an 8 MiB session records zero cache writes for exact
hits, close/reopen, unchanged refreshes, and sub-threshold preview appends. On
the validation host, a 64 KiB preview append wrote 98,860 bytes through the main
database and rollback journal; a small session-metadata append wrote 16,924
bytes and a history append wrote 25,124 bytes. CI enforces bounded byte budgets
rather than these host-specific exact values, ensuring write volume stays tied
to changed rows instead of total conversation size.

## NFS, concurrency, and failure behavior

- Removing WAL avoids SQLite's shared-memory WAL requirement on NFS. The real
  Linux CI smoke mounts an NFSv3 export with locking enabled, starts two test
  processes against the same cache, exercises discovery and preview appends,
  and requires `integrity_check=ok` with no WAL, SHM, or leftover journal.
- Local multi-process tests race six preview writers and separately cover two
  cold builders, stale append writers, database-busy fallback, and identical
  catalog writers. Compare-and-swap losers perform no cache-page writes.
- A busy or read-only cache returns source-derived results promptly. Partial
  JSONL tails are read without persisting an incomplete cursor.
- TUI shutdown and history command completion explicitly close catalog and
  preview handles. Other long-lived in-process callers can close a finished
  Codex root through the same lifecycle API, which is required before deleting
  that root on Windows.
- The long-running Teams bridge owns that lifecycle explicitly: it keeps the
  handles hot while listening and releases them when the listener exits.
  Direct history-watch tests close the process-global cache before temporary
  directory cleanup, covering Windows' stricter open-file semantics.
- Missing source files do not create a cache database. Symlinked or non-regular
  cache paths are rejected instead of followed.
- `CODEX_HELPER_PREVIEW_CACHE_BACKEND=off` remains available for diagnosis. The
  former `json` value now resolves to SQLite so it cannot silently restore the
  whole-file writer.

## Validation added

- Full repository tests and `go vet` pass.
- The complete `internal/codexhistory` suite passes under the race detector.
- Windows amd64 and macOS arm64 test binaries cross-compile successfully.
- Tests cover unified versioning, automatic location, effective-user isolation,
  one-time legacy cleanup, ordinary same-version reuse, permissions, symlink
  rejection, corruption and malformed-schema rebuilds, read-only and busy

  memory bounds, two-TUI conflicts, and multi-process idempotence.

  bounded rollback-journal bytes for required mutations.
- Mandatory Linux CI adds the real mounted-NFS concurrency and integrity smoke;
  existing Linux, macOS, and Windows release matrices continue to exercise TUI
  preview and history behavior.
