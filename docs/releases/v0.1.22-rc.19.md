# v0.1.22-rc.19

## Why

Teams history recovery could remain permanently blocked after Codex replaced a
legacy rollout with a paginated rollout. The old raw history file must remain
untouched, while the helper still needs a trusted cursor before it can resume
automatic synchronization.

## What changed

- Detects a Codex paginated rollout only after validating its session identity
  and stable file identity.
- Streams the replacement history to locate the previously trusted final or
  transcript record, then rebases the durable checkpoint to that anchor.
- Records one recovery attempt per replacement identity when the anchor cannot
  be proven, avoiding repeated scans of the same large history file.
- Preserves completion-pending, unresolved-execution, and outbox state; rebase
  never rewrites raw Codex history or creates delivery rows.
- Keeps legacy files on the existing fail-closed recovery path and persists the
  new recovery identity through both JSON and SQLite projections.

- `go vet ./internal/teams ./internal/teams/store`
- `go test ./...`

## Compatibility

The change is backward compatible with existing JSON and SQLite state. Legacy
Codex history remains readable by Codex and is never rewritten by the helper;
only a Codex-produced paginated replacement with a verifiable anchor is
automatically adopted. Teams delivery and execution fences remain intact, and
no public Teams message protocol changes.
