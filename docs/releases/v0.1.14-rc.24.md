# v0.1.14-rc.24

## Why this prerelease exists

This candidate contains the Teams/OneDrive durable file-transfer change from
`v0.1.14-rc.23`, plus a cross-platform correction found by the prerelease
workflow itself. The previous candidate passed the Linux implementation tests
but its Windows release preflight exposed a cleanup bug: a successful download
could leave its `.part.lock` file behind because Windows does not permit an
open lock-file handle to be unlinked.

The correction is intentionally small and keeps the transfer protocol
unchanged. The lock is released before its pathname is removed, and cleanup is
attempted only after a successful unlock. A failed unlock leaves the lock
residue in place rather than risking a second writer.

## File-transfer behavior

- Files at or below 10 MiB use one Graph upload request. Larger files use a
  resumable Graph upload session with sequential 10 MiB chunks. The chunk size
  is a multiple of Graph's 320 KiB fragment unit and is independent from the
  separate 250 GB application single-file ceiling.
- File bodies do not inherit the 30-second whole-request control timeout.
  They use bounded connection and response-header timeouts, an idle-body
  watchdog that resets on progress, bounded retries, and a small per-host
  transport pool. Uploads remain sequential so one transfer cannot create a
  connection or port storm.
- Outbound attachments are staged privately, hashed with SHA-256, and tracked
  in a durable outbox. Upload-session URL, expiry, acknowledged offset, and
  DriveItem publication are checkpointed with attempt fencing. A restart can
  resume a valid session; malformed or regressed server offsets fail closed.
  A local lease heartbeat renews the outbox during a long chunk without making
  extra Graph requests or parallelizing the upload.
- Downloads stream into a private `.part` file with metadata and an exclusive
  lock, resume only after validating `206` and `Content-Range`, refresh expired
  preauthenticated URLs, call `fsync` before preserving partial data, and
  publish only after final size/range checks. Successful publication now
  releases the lock before removing `.part.lock`, which works on both Unix and
  Windows and preserves serialization for waiters that already opened the
  lock inode.
- Helper-generated messages carry an internal provenance marker, but the
  marker is accepted only when it matches a durable outbox record for the same
  chat, message ID, attachment, and live transfer state. A marker alone is
  never enough to suppress a user message.
- Startup reconciliation cleans abandoned staged files without following
  symlinks or deleting paths outside the configured outbox. Temporary files
  use private names and are published without replacing an existing artifact.

## Reliability and compatibility

The 30-second timeout remains for Graph metadata, upload-session creation, and
Teams message POST control operations. It is not a deadline for a file body
that is making progress. The transfer implementation uses no background
worker or listener, keeps its connection pool bounded, and does not create a
new process or port per chunk. Direct `send-file` remains compatible with the
existing scoped outbound provenance ledger; the durable outbox is authoritative
for bridge and automatic attachment delivery.

## Validation

The implementation was validated with:

- `go test ./...` and `go test -race ./...` on the original durable-transfer
  candidate;
- `go vet ./...`, `git diff --check`, and Windows amd64 cross-compilation of
  the affected packages;
- complete `go test ./internal/teams ./internal/teams/store -count=1` after
  the lock-cleanup correction;
- focused race tests covering crash-partial resume and concurrent destination
  locking;
- the prerelease workflow's Windows, Linux, macOS, container, installation,
  and transfer/provenance preflight matrices.

This is a prerelease for validating the Teams file-transfer path. It does not
replace the existing stable `v0.1.14` release.
