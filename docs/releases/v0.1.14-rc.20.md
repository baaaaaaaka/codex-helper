# v0.1.14-rc.20

## Why this prerelease exists

`v0.1.14-rc.19` hardened proxy recovery, but follow-up testing found two
remaining lifecycle boundaries that could still make an otherwise successful
update or recovery look broken. First, an explicit request such as
`cxp upgrade --version v0.1.14-rc.19` could be re-entered through the old stable
launcher during verification. Because the stable `v0.1.14` is newer in
SemVer ordering than its own prerelease, the stable launcher could reactivate
`v0.1.14` and make candidate verification report the wrong version. Second,
the detached proxy launcher could start a child without retaining ownership of
the child's wait state, leaving exited children unreaped on Unix and making
failure cleanup less deterministic.

This candidate makes the selected update target and the proxy process owner
explicit across restart boundaries. It is intended to keep TUI and desktop
proxy behavior stable while making network recovery, process cleanup, and
stable-to-prerelease updates converge safely.

## What changed

- Treat an explicit `--version` as an exact target, including stable-to-
  prerelease and prerelease-to-stable transitions. The immutable runtime now
  owns activation and verification; the stable entry cannot silently undo the
  requested target merely because its SemVer is higher.
- Preserve the managed stable launcher contract during rollback and retry.
  Windows sharing violations are recorded as a bounded deferred repair tied to
  the parent process, while the stable dispatcher remains able to verify and
  route to the newly activated immutable runtime. Unrelated user-authored
  shims and immutable runtime files are not overwritten.
- Make candidate update reconciliation idempotent and restart-safe across
  partial activation, pending state, repeated invocation, process failure, and
  locked Windows entry files. Verification is performed by executing the fresh
  managed entry, not by trusting a port, pointer, or filename alone.
- Retain the detached proxy child's wait ownership until it exits. Failed
  startup paths terminate and wait for owned children before returning, and
  successful daemon records are cleaned when the child exits. This prevents
  orphaned/reaped-state leaks without adding another steady-state process.
- Keep the proxy recovery invariants from `rc.19`: a stable HTTP listener,
  active/candidate generation fencing, single-flight probes, bounded retries,
  process-tree ownership, route-aware loop detection, DNS-alias and hop-limit
  checks, and bounded resource behavior.

## Test and CI coverage

The release candidate is qualified with:

- `go test ./... -count=1`
- race-enabled tests for candidate updates, runtime dispatch, HTTP proxy,
  stack, SSH, and CLI lifecycle paths;
- Docker SSH/SOCKS fault injection covering peer restart, network rebuild,
  100% packet loss, recovery, concurrent CONNECT traffic, chain loops,
  aliases, hop limits, and cleanup;
- Windows amd64 compilation of the CLI, proxy, candidate-update, and runtime
  test packages, plus macOS amd64 compilation of the CLI and local proxy;
- GitHub Actions workflow validation with `actionlint`;
- hosted Ubuntu, macOS, and Windows loopback/fault-lab jobs, native Windows
  lifecycle checks, Docker recovery checks, bounded resource checks, and the
  release upgrade-compatibility matrix.

The hosted jobs can deterministically reproduce transport loss, resume and
probe events, generation replacement, locked-entry update behavior, and
process cleanup. They cannot physically close a laptop lid or hibernate a
GitHub-hosted VM; the macOS/Windows native jobs therefore validate the
platform-specific process and launcher contracts while the loopback and
Docker jobs provide the deterministic sleep/network-failure simulation.

This is a prerelease. It does not replace the existing `v0.1.14` stable
release. Existing helpers can opt in with `helper update prerelease`.
